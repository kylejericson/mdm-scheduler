This tool can lock and wipe managed devices on a schedule. Scope its API Role to only the actions you intend to use, and put the UI behind TLS if it is reachable beyond your own network.

Jamf Pro

1. Create an API Role

In Jamf Pro: Settings → System → API roles and clients → API Roles → New. Add the privileges below — Jamf checks reads and writes separately, and MDM commands need three different kinds of privilege at once.

Always required

PrivilegeWhy
Read PoliciesPopulate the policy dropdown
Read macOS Configuration ProfilesPopulate the macOS profile dropdown
Read iOS Configuration ProfilesPopulate the mobile profile dropdown
Read Smart Computer GroupsGroup targets (smart)
Read Static Computer GroupsGroup targets (static) — separate privilege from the smart one
Read Smart Mobile Device GroupsMobile group targets (smart)
Read Static Mobile Device GroupsMobile group targets (static)

Per action

PrivilegeEnables
Update PoliciesEnable/disable a policy, and change a policy's scope
Update macOS Configuration ProfilesAssign/unassign a macOS profile to a computer group
Update iOS Configuration ProfilesAssign/unassign a mobile profile to a device group

Scope lives on the policy or profile object, so the Update … Computer Groups privileges are not needed — this tool never edits a group's definition.

MDM commands - all three of these

  1. View MDM command information in Jamf Pro API — required by every /api/v2/mdm/ endpoint. Careful: the near-identical Send MDM command information in Jamf Pro API does not satisfy it. Picking the wrong one gives 403 INVALID_PRIVILEGE.
  2. Read Computers and/or Read Mobile Devices — every run does one inventory sweep to turn IDs and serial numbers into management IDs and to check whether each device can actually take the command. Without it you get 401 on every command, however many Send privileges you have.

2. Create an API Client

API roles and clients → API Clients → New. Assign the role you just made, enable the client, then generate a client secret — Jamf shows it once. Leave the client unscoped from Sites unless you mean to restrict it; a Site-scoped client silently sees fewer objects, which looks identical to missing privileges.

3. Add the instance here

Instances → Add instance. Base URL is the full canonical host (https://yourorg.jamfcloud.com, no trailing path). Choose API Client, paste the client ID and secret, save, then press Test. A healthy result names your Jamf Pro version and counts what it can see.

Iru

Iru is the current name for what was Kandji. Its API still answers on the api.kandji.io hostnames as well as api.iru.com; either works.

1. Create an API token

In Iru: Settings → Access → API tokens → Add Token. Tokens are tenant-level bearer tokens with per-endpoint permissions, so enable only what you schedule. Copy the token when it is shown - Iru does not show it again.

PermissionNeeded for
Device listResolving serial numbers, blueprint membership, the pre-flight check
Blueprint listThe blueprint dropdowns
Update deviceMoving a device to another blueprint
The specific device actions you scheduleLock, erase, restart, blank push, and so on - each is its own permission

2. Find your API URL

Also under Settings → Access. It looks like https://yourtenant.api.kandji.io (US) or https://yourtenant.api.eu.kandji.io (EU). Paste it as the instance Base URL exactly as shown, with no trailing path.

Commands available: {{ iru_commands.keys() | join(', ') }}

Blueprints: there is no "unassign"
Every Iru device belongs to exactly one blueprint, and the API only sets which one. Taking a Mac out of a blueprint therefore means moving it into another - point the schedule at a destination blueprint and the devices that are already there are left alone. Deleting a device from Iru is a different, destructive operation and is not wired into this tool.

Targeting

  • Specific devices - serial numbers (what you'll usually have) or Iru device UUIDs, comma separated.
  • Blueprint - every device in it, read when the job fires.
  • Devices whose MDM is not enabled, or that have been removed from Iru, are skipped and named in the run log.

Worth knowing

  • Locking a Mac returns an unlock PIN that Iru generates. It is recorded in the run log - without it you cannot unlock the machine.
  • Erase needs a 6-digit PIN for Macs; it is ignored for iOS, iPadOS and tvOS.
  • Iru actions are one API call per device, so a large blueprint means a lot of calls. The tenant limit is 10,000 requests per hour.
  • A command that is already pending on a device comes back as 400 Command already running.
  • Unlock Account and Delete User need a local username; Set Name needs a device name.

Both platforms

Targeting devices

  • Group — membership is expanded when the job fires, not when you save it, so smart groups stay current.
  • Specific devices — a comma-separated list of Jamf IDs and/or serial numbers, mixed freely. Digits are read as IDs, anything else as a serial.
  • Devices that are unmanaged or not MDM-capable are skipped and named in the run log; the rest still get the command.

Notes worth knowing

  • Scope changes are read-modify-write: the current group list is fetched, one group added or removed, and the whole list written back. A scope edit made in the Jamf console between the read and the write is overwritten.
  • Computer lock and wipe require a 6-digit PIN. Mobile wipes don't take one.
  • Wipes send returnToService.enabled = false; erased Macs won't auto-re-enroll.
  • A one-shot schedule pauses itself after a successful run so its history stays visible. Run now never auto-pauses.
  • If the container is down at fire time, the run happens on startup within a one-hour grace window, then is skipped.
  • Times are stored in UTC and shown in each schedule's own timezone.
